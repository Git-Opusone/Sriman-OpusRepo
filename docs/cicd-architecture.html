Step-by-Step Detail
1

Checkout Code — actions/checkout@v4

Downloads the full repository onto the GitHub Actions runner VM. All subsequent steps operate on this code.

2

Configure AWS Credentials — aws-actions/configure-aws-credentials@v4

Injects AWS_ACCESS_KEY_ID and AWS_SECRET_ACCESS_KEY from GitHub Secrets into the runner environment, allowing all subsequent AWS CLI and Docker commands to authenticate against us-west-2.

3

Login to Amazon ECR — aws-actions/amazon-ecr-login@v2

Performs docker login to the ECR registry using the AWS credentials from step 2. After this, Docker commands can push images to the private registry.

4

Build & Push Docker Image

Runs three Docker commands in sequence:

docker build -t $ECR_REGISTRY/opus-ecr:$SHA . — builds image using Dockerfile
docker tag ... :latest — also tags with :latest alias
docker push both the SHA tag and the :latest tag to ECR
5

Deploy — Copy Monitoring Config to EC2 — appleboy/scp-action@v0.1.7

Copies the monitoring stack files (docker-compose.yml, .env template) from the repo to ~/opus-monitoring/ on the EC2 instance over SCP before the SSH deploy step runs. Uses EC2_HOST and EC2_SSH_KEY secrets.

6

Deploy — SSH into EC2 — appleboy/ssh-action@v1.0.3

SSHes into the EC2 instance and runs the full deployment script in sequence:

Create docker network opus-monitoring (if not exists)
ECR login on EC2 — aws ecr get-login-password | docker login
Pull latest image — docker pull $ECR_REGISTRY/opus-ecr:latest
Stop & remove existing container — docker stop opus-one-app && docker rm opus-one-app
Start fresh container — docker run -d with all env vars (see Section 4)
Write monitoring .env from Grafana secrets, then docker compose up -d in ~/opus-monitoring/
Prune old images — docker image prune -f
Diagnostics — docker ps and docker logs alloy --tail 20

2. Docker & Build

How the application is packaged into a Docker image. Uses system Chromium — saves 300 MB vs bundled Playwright browser.

📋
Dockerfile Overview
BASE

Base Image — node:20-slim

Debian Bookworm slim variant. Minimal OS — all extra system packages are installed explicitly.

PKG

System Packages — Playwright Dependencies

Installs chromium plus all required shared libraries:

ca-certificates, fonts-liberation, libatk-bridge2.0-0, libatk1.0-0, libcups2, libdbus-1-3, libdrm2, libgbm1, libglib2.0-0, libgtk-3-0, libnss3, libx11-6, libxcomposite1, libxdamage1, libxext6, libxfixes3, libxrandr2, libxshmfence1, xdg-utils
ENV

Environment — Skip Playwright Browser Download

PLAYWRIGHT_BROWSERS_PATH=/usr/bin
PLAYWRIGHT_SKIP_BROWSER_DOWNLOAD=1
Points Playwright at the system Chromium instead of downloading its own copy.

APP

Application Layers

COPY package*.json ./ — copy manifests first (cache layer)
npm ci --omit=dev — production deps only
COPY src/ ./src/ — copy application code
EXPOSE 3000 — declare listening port
CMD node src/server.js — entry point
💡
System Chromium — Why It Matters
300 MB saved — Playwright's bundled Chromium download is ~300 MB. Using the distro-installed chromium package eliminates that download step entirely and reduces final image size.
ApproachImage Size
Playwright base image + bundled Chromium~1.1 GB
node:20-slim + system Chromium~800 MB
Trade-off: System Chromium version is tied to Debian Bookworm's package repo. For most county site automation this is perfectly fine — Chromium 120+ handles all required JS.
⚡
Layer Caching Strategy

Docker caches each layer. The build order is intentional:

System packages installed first

Rarely changes — cached across almost all builds.

package.json copied + npm ci

Only re-runs when dependencies change. Most builds skip this.

src/ copied last

Changes on every code push — always a new layer but it's tiny (just JS files).

3. GitHub Secrets

All secrets required in Settings → Secrets and variables → Actions. The pipeline reads these at runtime — values never appear in logs.

Required: Every secret in this table must be set before the pipeline can succeed. Missing secrets cause the workflow step that references them to fail immediately.
🔐
All GitHub Secrets — Complete Reference
Secret Name Purpose Where Used
AWS_ACCESS_KEY_ID AWS IAM user access key — authenticates the runner to AWS services configure-aws-credentials step (Job 1)
AWS_SECRET_ACCESS_KEY AWS IAM user secret key — paired with the access key above configure-aws-credentials step (Job 1)
EC2_HOST EC2 instance IP address or hostname (e.g. 34.208.134.96) SSH step + SCP step (Job 2)
EC2_SSH_KEY Full contents of the EC2 SSH private key (.pem file) SSH step + SCP step (Job 2)
ECR_REGISTRY Full ECR registry URL (e.g. 393060838208.dkr.ecr.us-west-2.amazonaws.com) docker pull on EC2 (Job 2 deploy script)
OPENAI_API_KEY OpenAI API key — enables GPT-4o-mini AI fallback agent for complex search forms App env var passed in docker run (Job 2)
CAPSOLVER_API_KEY NEW CapSolver credit-based API key for solving Cloudflare Turnstile + JS challenges App env var passed in docker run (Job 2)
GRAFANA_PROM_URL Prometheus remote-write endpoint URL for Grafana Cloud Written to ~/opus-monitoring/.env at deploy time
GRAFANA_PROM_USER Prometheus auth username (numeric instance ID) Written to ~/opus-monitoring/.env at deploy time
GRAFANA_LOKI_URL Loki log push endpoint URL for Grafana Cloud Written to ~/opus-monitoring/.env at deploy time
GRAFANA_LOKI_USER Loki auth username (numeric instance ID) Written to ~/opus-monitoring/.env at deploy time
GRAFANA_API_KEY Grafana Cloud API key used for both Prometheus and Loki authentication Written to ~/opus-monitoring/.env at deploy time
CAPSOLVER_API_KEY — Last-Resort Tier-2 Only
This key is only invoked as a paid last resort after the Tier-1 free CAPTCHA bypass fails. Tier-1 (25-second wait + iframe click) is completely free and handles approximately 90% of Cloudflare challenges encountered across TX county sites. CapSolver is only called for Turnstile + JS challenges that survive the full Tier-1 bypass — typically fewer than 10% of encounters. Keep the account funded but expect minimal usage.
How to add a secret: GitHub repo → Settings → Secrets and variables → Actions → New repository secret. Paste the value. Secrets are write-only — you can update or delete but never read back.
How secrets appear in logs: GitHub automatically redacts secret values in all workflow logs, replacing them with ***. You can safely check the logs without exposing credentials.

4. EC2 Deployment

The exact docker run command and monitoring stack configuration deployed on every pipeline run.

🐳
docker run Command — App Container
docker run -d \
  --name opus-one-app \
  --restart unless-stopped \
  --network opus-monitoring \
  -p 3000:3000 \
  -e OPENAI_API_KEY="${{ secrets.OPENAI_API_KEY }}" \
  -e OPENAI_MODEL="gpt-4o-mini" \
  -e PORT="3000" \
  -e BROWSER_HEADLESS="true" \
  -e MAX_CONCURRENT_SEARCHES="3" \
  -e SEARCH_TIMEOUT_MS="180000" \
  -e CACHE_TTL_HOURS="4" \
  -e CACHE_MAX_SIZE="1000" \
  -e CAPSOLVER_API_KEY="${{ secrets.CAPSOLVER_API_KEY }}" \
  $ECR_REGISTRY/$ECR_REPOSITORY:latest
--network opus-monitoring
Attaches the app container to the shared Docker network, allowing Grafana Alloy to scrape the app's /metrics endpoint and read container logs directly.
--restart unless-stopped
Docker automatically restarts the container if it crashes or if the EC2 server reboots, ensuring continuous uptime without manual intervention.
📊
Monitoring Stack Deploy — ~/opus-monitoring/

The SCP step (Step 5) copies the monitoring compose file to the server, then the SSH step writes the .env and starts the stack:

# Write .env from GitHub Secrets
cat > ~/opus-monitoring/.env <<EOF
GRAFANA_PROM_URL=${{ secrets.GRAFANA_PROM_URL }}
GRAFANA_PROM_USER=${{ secrets.GRAFANA_PROM_USER }}
GRAFANA_LOKI_URL=${{ secrets.GRAFANA_LOKI_URL }}
GRAFANA_LOKI_USER=${{ secrets.GRAFANA_LOKI_USER }}
GRAFANA_API_KEY=${{ secrets.GRAFANA_API_KEY }}
EOF

# Start / update monitoring stack
cd ~/opus-monitoring
docker compose up -d --remove-orphans
docker-compose.yml services:
  • opus-alloy — Grafana Alloy agent
  • node-exporter — system metrics
Network: opus-monitoring (external)
Declared as external: true in compose so both the app container and monitoring containers share the same network bridge — enabling direct container-to-container scraping.
Diagnostics at end of deploy:
docker ps — verify all containers running
docker logs alloy --tail 20 — confirm Alloy connected to Grafana Cloud
🔢
Post-Deploy Cleanup
docker image prune -f
Removes all dangling (untagged) images after each deploy. Prevents disk exhaustion on the EC2 instance over time — each 800 MB deploy would otherwise accumulate.
docker ps (verify)
Lists running containers. The pipeline output shows this in the Actions log so you can confirm opus-one-app, alloy, and node-exporter are all Up.
Alloy log check
Tails the last 20 lines of the Alloy container log. Confirms successful connection to Grafana Cloud endpoints and that metrics/logs are flowing.

5. Monitoring Stack

Three components collect and ship telemetry to Grafana Cloud. All run on the same Docker network as the app.

🔭
Grafana Alloy
Container: opus-alloy

The central telemetry agent. Collects from multiple sources and ships to Grafana Cloud.

Metrics scraping:
Scrapes http://opus-one-app:3000/metrics (Prometheus format) on a 15s interval. Also scrapes node-exporter on port 9100.
Log collection:
Reads Docker container logs from the Docker socket, adds labels (container name, job), and ships to Grafana Cloud Loki.
⚙️
node-exporter
Container: node-exporter

Exports EC2 host-level system metrics in Prometheus format on port 9100.

Metrics exported:
  • CPU usage per core
  • Memory / swap utilization
  • Disk I/O and filesystem usage
  • Network bytes in/out
  • System load average
📈
App Metrics Endpoint
src/shared/metrics.js

The app exposes a GET /metrics endpoint in Prometheus text format, implemented with prom-client.

Metrics tracked:
  • Search requests total (by county, platform)
  • Search duration histogram
  • Concurrent searches in flight
  • CAPTCHA encounters (Tier-1 vs Tier-2)
  • Cache hit / miss ratio
  • Error rate by handler

New / Updated Files — V3.0
captchaDetector.js — UPDATED
Refactored to implement the two-tier CAPTCHA resolution strategy. Tier-1 is the free bypass (25s wait + Cloudflare iframe click). Tier-2 calls captchaSolver.js only if Tier-1 fails. Also handles navigation-based CAPTCHA resets and detects cookie consent overlays separately from actual CAPTCHAs.
captchaSolver.js — NEW
Thin REST client for the CapSolver API. Submits Cloudflare Turnstile tasks, polls for the solution token, and injects it into the page. Only instantiated when CAPSOLVER_API_KEY is set and Tier-1 has already failed.
tax/routes.js — UPDATED
Updated to wire captchaDetector into the shared browser context. SSE streaming endpoint improvements for real-time progress events during multi-county batch searches.
🔄
CAPTCHA Tier Strategy
T1

Tier-1 — Free Bypass (~90% success)

Wait 25 seconds for Cloudflare challenge to complete, then click the Turnstile iframe checkbox. Works for cookie-based Cloudflare challenges that don't require JS proof-of-work. Zero cost.

T2

Tier-2 — CapSolver (~remaining 10%)

If Tier-1 fails (challenge still present), submit a CapSolver task with the site key. CapSolver solves the Turnstile + JS challenge and returns a token. Injected into the page to unblock navigation. Paid per solve.

7. Environment Variables

All environment variables consumed by the running container. Set via -e flags in the docker run command, sourced from GitHub Secrets.

📋
Complete Environment Variable Reference
Variable Default Description
OPENAI_API_KEY required OpenAI API key for GPT-4o-mini. Used by the AI vision fallback agent (vision.js) to analyze county search form screenshots and determine what to fill/click.
OPENAI_MODEL gpt-4o-mini OpenAI model name. gpt-4o-mini provides the best cost/performance ratio for screenshot analysis — fast vision inference at low per-token cost.
PORT 3000 TCP port the Express HTTP server listens on inside the container. Exposed and mapped 3000:3000 in docker run.
BROWSER_HEADLESS true Playwright headless mode. Must be true in production (no display server on EC2). Set to false only for local debugging with a visible browser window.
MAX_CONCURRENT_SEARCHES 3 Maximum number of Playwright browser sessions open at once. The concurrency gate in server.js queues requests beyond this limit. t3.medium RAM (4 GB) supports 3 concurrent Chromium instances comfortably.
SEARCH_TIMEOUT_MS 180000 Per-search timeout in milliseconds (3 minutes). If a county site fails to respond or a CAPTCHA cannot be solved within this window, the search is aborted and an error is returned.
CACHE_TTL_HOURS 4 Lifetime of each LRU cache entry in hours. Cached results avoid redundant browser sessions for the same property lookup within the TTL window.
CACHE_MAX_SIZE 1000 Maximum number of entries the LRU cache holds before evicting the least recently used. 1000 entries at typical payload size stays well within available memory.
CAPSOLVER_API_KEY NEW optional CapSolver API credit key. If absent, Tier-2 CAPTCHA solving is disabled and the app falls back to returning an error for unsolvable Cloudflare challenges.
Only used as Tier-2 last resort after Tier-1 free CAPTCHA bypass fails. Expected usage is less than 10% of CAPTCHA encounters.
Local development (.env file):
When running locally with npm start, create a .env file in the repo root with these same variable names. The dotenv package loads them at startup. Never commit .env to git — it is in .gitignore.
Production (docker run -e flags):
In production, there is no .env file. All variables are injected directly via -e KEY="VALUE" arguments in the docker run command, which reads the values from GitHub Secrets at deploy time.
