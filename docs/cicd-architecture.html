1. High-Level Overview

What is CI/CD and what does it mean for this project?

What is CI/CD in plain English?
CI/CD stands for Continuous Integration / Continuous Deployment. It means: every time you save and push your code to GitHub, a robot (GitHub Actions) automatically tests, packages, and deploys your application to the live server — with zero manual steps from you. You write code → push → it goes live automatically.
💻
You (Developer)

Write code in VS Code on your laptop. When ready, run 3 git commands. That's your entire job.

git add .

git commit -m "message"

git push
🤖
GitHub Actions (Robot)

Automatically wakes up when you push. Builds your app into a Docker image, uploads it to AWS, and restarts the live server. Takes ~4 minutes.

☁️
AWS (Live Server)

Your application runs 24/7 on an EC2 server in Oregon. Users access it at http://44.253.126.67. Nginx routes traffic into the app.

3. Detailed CI/CD Flow — Step by Step

Exactly what happens, in order, from your push to the live server.

Phase 1 — Developer Action (You)

You write code changes locally

Edit files in VS Code. The app runs on localhost:3000 for testing with npm start.

git add . → stages your changes

Tells git "these are the files I want to include in my next save point."

git commit -m "message" → saves a snapshot

Creates a permanent save point in git history with a description. Like a game save.

git push → sends to GitHub

Uploads your commit to the GitHub repository online. This is what triggers the pipeline.

Phase 2 — GitHub Actions (Automatic Robot)

GitHub detects the push

GitHub sees code was pushed to branch claude/mortgage-search-microservice-klXBo and wakes up the workflow.

deploy.yml starts running

GitHub spins up a fresh Ubuntu virtual machine (called a "runner"). Your deploy.yml instructions run on it.

Job 1: Build & Push Docker Image (~2 min)

The runner downloads your code, reads the Dockerfile, and builds a self-contained Docker image of your entire app including Node.js, Playwright, Chromium, and all your code.

Image tagged and pushed to ECR

The image gets two tags: one with the exact commit SHA (unique ID) and one called "latest". Both are pushed to AWS ECR (your private Docker image storage).

Job 2: Deploy to EC2 (~36 sec)

GitHub Actions SSHs into your EC2 server, logs into ECR, pulls the new image, stops the old container, and starts a fresh container with the new image.

Pipeline complete — app is live

The new version of your app is now running on 44.253.126.67. GitHub shows a green checkmark.

4. GitHub Actions — deploy.yml Explained

File location: .github/workflows/deploy.yml — This is the brain of the CI/CD pipeline.

What is deploy.yml? It is a recipe file written in YAML format. It tells GitHub's robot exactly what to do, step by step, every time you push code. Think of it as a cooking recipe — GitHub follows it exactly.
📋
Full deploy.yml with Line-by-Line Explanation
SECTION 1: When to run — The trigger condition 
name: Build & Deploy to AWS EC2   # Name shown in GitHub Actions tab

on:
  push:
    branches:
      - main
      - claude/mortgage-search-microservice-klXBo  # Run when code is pushed to THIS branch
  workflow_dispatch:   # Also allow manual trigger from GitHub website (button click)
SECTION 2: Global variables — Values reused throughout the file 
env:
  AWS_REGION: us-west-2        # Oregon region — where your EC2 and ECR live
  ECR_REPOSITORY: opus-ecr     # Name of your ECR repository (Docker image storage)
  CONTAINER_NAME: opus-one-app # What to name the running Docker container on EC2
SECTION 3: Job 1 — Build & Push Docker Image 
jobs:
  build-and-push:
    name: Build & Push Docker Image
    runs-on: ubuntu-latest   # GitHub spins up a fresh Ubuntu virtual machine for this

    steps:
      # Step 1: Download your code onto the runner VM
      - name: Checkout code
        uses: actions/checkout@v4

      # Step 2: Give the runner permission to talk to AWS
      - name: Configure AWS credentials
        uses: aws-actions/configure-aws-credentials@v4
        with:
          aws-access-key-id: ${{ secrets.AWS_ACCESS_KEY_ID }}      # From GitHub Secrets
          aws-secret-access-key: ${{ secrets.AWS_SECRET_ACCESS_KEY }} # From GitHub Secrets
          aws-region: us-west-2

      # Step 3: Login to ECR (so Docker can push the image there)
      - name: Login to Amazon ECR
        id: login-ecr
        uses: aws-actions/amazon-ecr-login@v2

      # Step 4: Build the Docker image, tag it, and push to ECR
      - name: Build, tag, and push image to ECR
        env:
          ECR_REGISTRY: 393060838208.dkr.ecr.us-west-2.amazonaws.com
          IMAGE_TAG: ${{ github.sha }}  # Unique ID = the git commit hash (e.g. 4d8f67b)
        run: |
          # Build the image using Dockerfile in the repo root
          docker build -t $ECR_REGISTRY/opus-ecr:$IMAGE_TAG .

          # Also tag it as "latest" (so EC2 always pulls the newest)
          docker tag $ECR_REGISTRY/opus-ecr:$IMAGE_TAG $ECR_REGISTRY/opus-ecr:latest

          # Push both tags to ECR
          docker push $ECR_REGISTRY/opus-ecr:$IMAGE_TAG
          docker push $ECR_REGISTRY/opus-ecr:latest
SECTION 4: Job 2 — Deploy to EC2 — Only runs after Job 1 succeeds 
  deploy:
    name: Deploy to EC2
    runs-on: ubuntu-latest
    needs: build-and-push   # IMPORTANT: waits for Job 1 to finish successfully

    steps:
      # SSHs into your EC2 server and runs the deployment commands
      - name: Deploy to EC2 via SSH
        uses: appleboy/ssh-action@v1.0.3
        with:
          host: ${{ secrets.EC2_HOST }}      # 44.253.126.67
          username: ubuntu
          key: ${{ secrets.EC2_SSH_KEY }}    # Contents of your .pem key file
          script: |
            # 1. Login to ECR from the EC2 server
            aws ecr get-login-password --region us-west-2 | \
              docker login --username AWS --password-stdin $ECR_REGISTRY

            # 2. Pull the new image
            docker pull $ECR_REGISTRY/opus-ecr:latest

            # 3. Stop and remove the OLD running container (ignore error if none)
            docker stop opus-one-app || true
            docker rm   opus-one-app || true

            # 4. Start a NEW container with the fresh image + all environment variables
            docker run -d \
              --name opus-one-app \
              --restart unless-stopped \    # Auto-restart if server reboots
              -p 3000:3000 \                # Map EC2 port 3000 to container port 3000
              -e OPENAI_API_KEY="..." \     # From GitHub Secrets
              -e OPENAI_MODEL="gpt-4o-mini" \
              -e PORT="3000" \
              -e BROWSER_HEADLESS="true" \
              -e MAX_CONCURRENT_SEARCHES="3" \
              $ECR_REGISTRY/opus-ecr:latest

            # 5. Clean up old images to save disk space
            docker image prune -f
What "actions/checkout@v4" means:
This is a pre-built action (reusable plugin) made by GitHub. It downloads your repository's code onto the runner virtual machine. @v4 means version 4.
What "${{ secrets.XYZ }}" means:
GitHub Secrets are encrypted values stored in your repo settings. The pipeline reads them at runtime. Nobody can see the actual values in the logs — they appear as ***.

5. Dockerfile — Packaging the Application

File location: Dockerfile (root of repo) — The recipe for building your application's container.

What is Docker? Docker is like a shipping container for software. Instead of installing Node.js, Playwright, and all dependencies on every server by hand, you pack everything into a single "image" (a snapshot). That image runs identically on any machine — your laptop, GitHub's server, AWS EC2. No more "it works on my machine" problems.
📋
Full Dockerfile with Explanation
# BASE IMAGE: Use Microsoft's official Playwright image
# This image already has Ubuntu + all system libraries Chromium needs
# Without this, you'd need to install 50+ system packages manually
FROM mcr.microsoft.com/playwright:v1.44.0-jammy

# Set the working directory inside the container
# All subsequent commands run from /app
WORKDIR /app

# ── LAYER CACHING TRICK ──────────────────────────────────────────────
# Copy package.json FIRST (before copying all your code)
# Docker caches each layer. If package.json hasn't changed,
# it skips the npm install step on next build = much faster rebuilds
COPY package*.json ./

# Install only production dependencies (not dev tools like nodemon)
RUN npm ci --only=production

# Install the Chromium browser that Playwright will control
RUN npx playwright install chromium

# ── COPY YOUR APPLICATION CODE ───────────────────────────────────────
# Now copy everything else (code files, public/, src/, data/, etc.)
# This is done AFTER npm install so code changes don't trigger reinstall
COPY . .

# Delete files not needed in production (saves image size)
RUN rm -rf .env.example docs scripts .vscode .claude

# ── SECURITY: Run as non-root user ───────────────────────────────────
# By default containers run as root (admin) which is dangerous
# Create a normal user "appuser" and switch to it
RUN groupadd -r appuser && useradd -r -g appuser appuser
RUN chown -R appuser:appuser /app
USER appuser

# Tell Docker this container listens on port 3000
EXPOSE 3000

# ── HEALTH CHECK ─────────────────────────────────────────────────────
# Docker checks this every 30 seconds to know if the app is alive
# If it fails 3 times, Docker marks the container as unhealthy
HEALTHCHECK --interval=30s --timeout=10s --start-period=60s --retries=3 \
  CMD node -e "require('http').get('http://localhost:3000/api/health', \
  (r) => r.statusCode === 200 ? process.exit(0) : process.exit(1))"

# The command that starts the app when container launches
CMD ["node", "server.js"]

Nginx — The Traffic Director

Nginx runs on EC2 as a reverse proxy. It sits in front of your app and routes incoming web traffic.

Why Nginx instead of exposing port 3000 directly?

  • Standard web port 80 (users don't need to type :3000)
  • Can add SSL/HTTPS easily with Certbot
  • Handles request timeouts (set to 300s for Playwright searches)
  • Can serve multiple apps on one server in future
  • Passes real user IP to the app
# /etc/nginx/sites-available/opus-one
server {
    listen 80;
    server_name _;

    # Long timeout for Playwright searches
    proxy_read_timeout 300s;

    location / {
        # Forward all traffic to Node.js
        proxy_pass http://localhost:3000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }
}

7. GitHub Secrets — Secure Configuration

Sensitive values stored encrypted in GitHub, injected into the pipeline at runtime.

What are GitHub Secrets? They are encrypted key-value pairs stored in your GitHub repository settings. They are NEVER visible in logs (shown as ***). The CI/CD pipeline reads them as environment variables at runtime. This is how we avoid hardcoding passwords in code files.

10. Troubleshooting Guide

Common issues and how to fix them.

SymptomLikely CauseFix
GitHub Actions shows red ❌ on "Build & Push" ECR repo doesn't exist, wrong region, or bad AWS keys Check ECR repo name matches deploy.yml. Verify AWS_ACCESS_KEY_ID secret is correct.
GitHub Actions shows red ❌ on "Deploy to EC2" SSH timeout (port 22 blocked) or wrong SSH key Check Security Group allows port 22 from 0.0.0.0/0. Verify EC2_SSH_KEY secret contains full .pem content.
44.253.126.67 shows "502 Bad Gateway" Nginx running but Docker container is stopped/crashed SSH into EC2 → docker logs opus-one-app → fix the error → docker restart opus-one-app
Container keeps restarting App crashes at startup — missing module or bad env var docker logs opus-one-app → read the error message
Old version showing after deploy Browser cache or old Docker image Hard refresh (Ctrl+Shift+R). On EC2: docker pull && docker restart
localhost:3000 not working npm start not running, or missing .env file Run npm start. Check .env file has OPENAI_API_KEY.
Search times out County website slow or Playwright crash Try again. Check docker logs for Playwright errors. County site may be down.
MODULE_NOT_FOUND error package.json missing a dependency Add the package to package.json dependencies, commit and push to rebuild.
