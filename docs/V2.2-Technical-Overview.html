Executive Summary

For directors and stakeholders — what the system does and what it has achieved

Orchestrate-Mortgage is a fully automated property tax and title search platform. Given an owner name or property identifier, the system autonomously navigates county assessor websites across the United States, extracts structured property records (owner, parcel ID, address, assessed value, tax status), and returns results to the caller — all without a human touching a keyboard.

The platform uses a combination of deterministic Playwright browser automation for the six dominant county software platforms and an AI fallback agent (GPT-4o-mini with vision and tool calling) for edge cases — ensuring coverage across every county regardless of platform.

The "One Agent → Many Agents" Concept Core Strategy

How a single AI agent was used to bootstrap nationwide county data at scale

The core insight behind Phase 2: the same AI agent that learned to search one county could be instructed to discover all counties. Instead of manually curating 3,200 URLs, we pointed the master agent at netronline.com — the authoritative directory of US county assessor links — and let it spawn sub-agents for each state. Each sub-agent applied the same "crawl, identify, extract URL" playbook across every county in its state. This is the foundational AI-first design principle of the platform.

🤖
Master AI Agent
GPT-4o-mini / Groq
Playwright + Vision
Task 1 — Source Identification Identify netronline.com as the authoritative US county assessor directory. Learn the site structure: state index pages, county listing pages, external assessor URL links.
Task 2 — State Sub-Agent Spawning (x50) For each of the 50 US states: spawn a sub-agent assigned to that state's netronline page. Sub-agent crawls each county entry, extracts the assessor/CAD URL, and flags the county name.
Task 3 — Platform Classification Each extracted URL is passed through platformDetector.detectFromUrl() to classify into: qpublic, tyler, beacon, patriot, vision, bis, or generic. This label is stored alongside the URL.
Task 4 — Data Consolidation All sub-agent results are merged into data/counties.json: one record per county with state, county name, assessor URL, and platform key. Live URL health checks flag dead links for netronline refresh.

URL Patterns
esearch.{county}cad.org/
{county}.bisconsultants.com/
{county}.cadcentral.com/
Key Challenge
SPA fires the /search/SearchResults XHR before Playwright can set up an intercept if form submit is called first. Additionally, direct re-fetching of the XHR URL always returns HTML (not JSON) because results are session-bound.
Solution
Set up page.waitForResponse() promise before triggering the form submit — Playwright queues the intercept before the network request fires. The intercepted response contains { resultsList, totalResults }. Direct URL re-fetch is never attempted.
Platform detection strategy: platformDetector.detectFromUrl() tests URL patterns first (synchronous, no network needed). If the URL is ambiguous, detectFromHtml() fingerprints the live page HTML for known strings like qpublic.schneidercorp, tylertech, patriotproperties, vgsi, or bisconsultants. The combined detectPlatform(url, html) function is the primary entry point used in browserAgent.js.

CAPTCHA Strategy

Detection, handling, and future upgrade path
Future

Option 1 — 2Captcha / CapSolver API

Pay-per-solve CAPTCHA solving service. Cost: approx. $0.001 per solve. Supports reCAPTCHA v2/v3, hCaptcha, Cloudflare Turnstile, image CAPTCHAs. Zero code changes required in handlers — only the resolver function needs swapping.

Planned for production when volume justifies the cost.

Current — V2.2

Option 2 — Detect & Flag (Implemented)

detectCaptcha(page) in src/captchaDetector.js. If a CAPTCHA is found, the search returns a captchaBlocked result. Frontend renders an amber warning card with an order note for manual resolution. No automated solving attempted.

Implemented across all 6 handlers and the AI fallback loop.

Rejected

Option 3 — User Prompt in Browser

Present the CAPTCHA to the end-user in a browser window for manual completion. Rejected due to poor UX (blocks the search UI), complex session handoff between Playwright and the user's browser, and incompatibility with headless server deployment.

Key Technical Challenges & Solutions

Root cause analysis and implemented fixes across all platform handlers
Challenge Root Cause Solution Handler(s)
Angular SPA returns 0 fields on extraction networkidle fires before Angular finishes rendering the DOM. Playwright declares the page loaded, but component content has not yet been injected into the HTML. waitForAngularContent() polls on a short interval until Angular-rendered label elements (e.g., ng-reflect-label) appear in the DOM. Only then does extraction proceed. qPublic, Beacon
Patriot search results invisible to Playwright The search form targets home-bottom.asp in a frameset. After submit, results appear in a different frame than the one Playwright is watching. Standard waitForNavigation sees no change. Playwright frame API: stay on frameset, submit inside the search frame, capture the bottom frame's redirected URL post-submit, then navigate the main page context there directly. Patriot
Patriot detail pages return 0 fields Summary.asp is itself a frameset. extractDetailFields() runs on the outer frameset HTML, which contains only <frameset> and <frame src=...> — no property data. Detect when a detail URL is a frameset. Loop through all child frames and run field extraction specifically on the frame whose src matches summary-bottom.asp. Patriot
Tyler sIndex stale data (all results show row 0) Tyler's server-side session uses an sIndex token. Clicking any result row in the results table consumes the sIndex. Subsequent requests using the same sIndex URL return row 0 data regardless of which row was intended. Pre-extract the row 0 detail during the initial results page load (before any click). For rows 1-N, record the table data only — navigating to their detail pages is a known server-side limitation. Tyler
Tyler produces wrong label/value pairs Adjacent table cells were extracted in sequence without checking which cells are labels vs. which contain data. Tyler Datalet tables mix label cells and value cells without consistent class markers. Only treat a cell as a label if it ends with a colon (:) or is a <th> element. findVal(header) provides flexible header matching against the parsed table. Tyler
BIS SPA search XHR not capturable The React SPA fires the /search/SearchResults XHR synchronously on form submit. If Playwright triggers the submit first, the network event fires before waitForResponse() is registered — the response is missed. Register the page.waitForResponse() promise handler before calling the form submit action. This ensures the Playwright intercept is in place before the network request fires. BIS
qPublic IP blocking (GA/Gwinnett sites) Some Georgia county qPublic deployments block non-US IPv6 ranges. The handler code is correct but requests from non-US servers are rejected at the network level. Handler code requires no changes. Deploy the service on a US-based server (any major cloud provider US region). IPv6 blocking at county level is a network policy — not a code issue. qPublic
Beacon delivers wrong search URL format counties.json entries sometimes contain PageTypeID=N&PageID=N in the Beacon URL (GIS map view). This format is ignored by Beacon's search controller and produces an empty or malformed search page. Beacon URL builder strips all PageTypeID and PageID query params from the stored URL and appends PageType=Search to force the correct search page. Beacon

Search Result Cache

In-memory LRU cache — eliminates redundant browser launches and OpenAI API calls for repeated searches

In production, mortgage order processing means thousands of searches hit the same counties, same owner names, and same property IDs repeatedly (e.g., multiple orders for properties in Harris County TX, or re-searches due to data corrections). Without a cache, every repeat search costs the same as the first — a full Playwright browser launch, 400–500 MB RAM, and 2–18 OpenAI API calls. The search cache eliminates this waste entirely.

Search error / timeoutNOT storedTransient failure — should not propagate to future requests
Entry older than TTLAuto-evictedStale data — next request triggers fresh live search
Cache at max size (1,000)LRU evictionOldest entry removed to make room for newest

Configuration (Environment Variables)

VariableDefaultDescription
CACHE_TTL_HOURS4How long a cached result is considered fresh (hours). Set to 8 for overnight batches, 1 for live data requirements.
CACHE_MAX_SIZE1000Maximum number of entries in memory. Each entry is ~50–200 KB depending on result size. 1,000 entries ≈ 50–200 MB RAM.

Future Upgrade Path

The current cache is in-process memory only — it resets on every server restart and is not shared across multiple server instances. For multi-server deployments, replace _searchCache (Map) in server.js with a Redis client using the same key/TTL logic. The interface is a drop-in replacement: GET / SET / EX (expire). No other code changes required.
